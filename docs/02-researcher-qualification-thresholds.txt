ASTR — Persistent Research Graphs & Incremental Updates

Implement this as a targeted performance improvement to the existing ASTR application. Do not redesign the UI or replace existing research, trading, or graph functionality.

1. Core objective

Make the Research Lab load its previously calculated graphs and metrics immediately when opened, instead of making the user wait for historical data to be fetched, recalculated, and rendered again.

Calculated results should be persisted and reused until the underlying data actually changes or a scheduled recalculation is due.

The experience should feel like opening a saved snapshot of the latest research results, with updates occurring in the background when necessary.

2. Real-money live trading: refresh every 5 minutes

Real-money trading is the exception to the normal research caching rules.

	•	Continue refreshing and verifying live trading information against the authoritative broker data every 5 minutes, using the existing scheduling infrastructure where possible.
	•	Keep live account balances, positions, executions, realized and unrealized P&L, and the live P&L graph as accurate and current as the available broker data allows.
	•	Reconcile against authoritative broker records instead of assuming cached values are correct.
	•	Recalculate live P&L when needed to verify accuracy, even when a change is not expected.
	•	Do not place, cancel, or modify orders simply because a refresh or recalculation runs.
	•	Do not trigger a complete Research Lab historical recalculation merely because live trading information was refreshed.
	•	Display the last successful refresh timestamp and clearly handle broker/API errors without presenting stale values as freshly verified.

Preserve existing live-trading safety rules, order execution logic, credentials, and account separation.

3. Researcher results: update only when necessary

Researcher historical results should not automatically recalculate every five minutes.

Historical researcher graphs and metrics

	•	Persist the latest successfully calculated historical researcher results.
	•	Load the saved results immediately when the Research Lab opens.
	•	Recalculate historical performance at the existing end-of-day processing point, after the relevant market data is available and validated.
	•	Recalculate earlier only when an actual relevant change requires it, such as a corrected historical bar, a changed trade record, or an intentional formula/configuration change.
	•	Do not recalculate unchanged historical periods simply because the user opens the page, changes tabs, or refreshes the browser.
	•	Preserve all existing researcher formulas, score thresholds, rankings, holding-period recommendations, and performance calculation rules.

Today’s researcher P&L and graphs

	•	Update today’s researcher P&L and today’s graph on the existing five-minute cadence only when necessary to satisfy the current-day reporting requirements.
	•	If a researcher buys or sells during the day, update the affected researcher’s current-day results as soon as the relevant event is recorded.
	•	If a relevant trade, fill, market bar, or other input changes, update only the affected researcher and dependent calculations.
	•	Do not recalculate every researcher’s entire historical performance for a single current-day trade.
	•	If nothing relevant changed, reuse the saved result.
	•	Maintain the existing distinction between realized P&L, unrealized P&L, and any other metrics currently displayed.

4. Incremental calculations

Use incremental updates wherever mathematically valid.

For rolling windows, retain the existing window and update the entering and leaving observations instead of rebuilding the entire window unnecessarily.

For example, for a 50-observation window, when observation 51 arrives, add observation 51 and remove observation 1. Continue with the next observation as new data arrives.

Apply this approach only where the existing formulas support it. Recalculate affected downstream values when a change requires it, and perform full recalculation when necessary to guarantee correctness.

Do not change the statistical meaning of any existing formula merely to improve performance.

5. Persistent cache and background processing

Inspect the existing database, server functions, caching, query invalidation, and scheduling architecture before implementing changes.

	•	Reuse existing infrastructure wherever possible.
	•	Persist computed results with their calculation timestamp, applicable researcher or strategy identifier, time range, and source-data version or freshness marker.
	•	Use a stable cache key that prevents live-trading results from being confused with researcher paper results.
	•	Load the most recent valid saved result immediately.
	•	Refresh or recalculate in the background without blocking the initial graph display.
	•	Replace the displayed snapshot only after the newer calculation succeeds.
	•	Prevent duplicate jobs and overlapping calculations from creating inconsistent results.
	•	Invalidate only the affected results when their dependencies change.
	•	If a background update fails, retain the last valid snapshot and clearly indicate that it may be stale.
	•	Never invent, interpolate, or fabricate P&L or historical performance to make a graph load faster.

Do not introduce unnecessary paid services, new APIs, or expensive infrastructure.
